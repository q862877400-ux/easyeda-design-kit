# Feature Specification: EasyEDA AI Design Kit（把「画出任意一块板」变成可安装、可验收的能力）

**Feature Branch**: `004-ai-pcb-design-kit`

**Created**: 2026-10-31

**Status**: Draft

**Input**: User description: "我需要一个产品：装上它之后，不管配什么模型、装在什么 harness 上，都能把客户给的电路板需求完整、顺利地画出来。它不应该是手搓的一堆一次性函数；主体是**把 EasyEDA 扩展中心已有的工具用熟，并把使用经验打包**；只有在扩展覆盖不了时才补充自有工具。"

## 背景与问题陈述

### 为什么需要这个产品

在此之前，同一块板被反复画过 49 轮，结果是：

| 现象 | 实测证据 |
|---|---|
| 每一轮都要临时造胶水 | 一次性脚本 **26 个**、一次性 playbook **28 个**，全部只服务一次 |
| 同一句纪律写进文档后仍被违反 | 「不要对着旧快照求解多对」写过 2 次，违反 2 次（第 43、46 轮） |
| 能力随会话消失 | 板子最好状态（未连 21 条）靠手搓达成，两次操作后退回 39 条 |
| 大量重复造轮子 | 手搓了布线器、DFM 检查器、丝印对齐、制造导出；而扩展中心已有 **PCB Auto Router**、**嘉立创下单检查**、**生成丝印**、**PCB Delivery Export** |

**结论**：缺的不是函数，是三层缺失——**决策层**（什么情境调哪个工具）、**验收层**（什么算画完）、**安装层**（能装到任意 harness / 发布到扩展中心）。

### 本产品是什么、不是什么

- **是**：一个可安装的能力包 + 一条可执行的验收 + 一份诚实的能力边界清单。装上它，模型能按文档把板子画完并自证；**不包含"从功能描述设计出正确电路"这一能力**。
- **不是**：新的 EDA 引擎、新的布线算法库、一堆针对性 MCP 工具。
- **代码的地位**：默认零自有代码。只有当扩展中心与命令层**实测覆盖不了**某个必需环节时，才补一个具名、可被索引、有验收的工具；并在边界清单里写明为什么补。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 陌生人装上包，只给需求就能画出合格板 (Priority: P1)

一位没用过本项目的用户：在 EasyEDA Pro 上装好本包要求的组件，把一段自然语言需求（例如"ESP32-S3 四层板：板载 5V 端子与 USB 供电、CH340 下载、BOOT/RESET、一颗 LED 带 +/− 丝印、四角 M3 孔"）交给任意一个接了本包的 Agent，得到一块**可打样**的板。

**Why this priority**: 这就是产品的全部意义。做不到它，其他都是附属。

**Independent Test**: 找一个从未参与本项目的执行者，只给需求文本与本包文档，不给任何预置坐标/BOM/UUID/网表，跑完整流程；由其只凭脚本回执复核。

**Acceptance Scenarios**:

1. **Given** 装好本包的环境与一段需求文本，**When** 执行设计流程，**Then** 产出含器件、网络、几何的工程，并逐阶段留下可复核回执。
2. **Given** 任一步骤失败，**When** 处理该步，**Then** 报告**具体失败阶段与原因**，且不会把失败报成通过。
3. **Given** 流程完成，**When** 跑验收，**Then** 电学连接零缺、DRC 零错误、DFM 零 ERROR、交付文件齐备。

---

### User Story 2 - 换模型、换 harness 结果一致 (Priority: P1)

同一条需求，换一个模型（或换一个 harness 外壳）重新执行，仍然能画出合格板；不允许出现"只有某个模型碰巧能做"的情况。

**Why this priority**: 产品的价值是**替代执行者的能力欠缺**；若依赖某个模型的手感，它就只是又一份一次性经验。

**Independent Test**: 同一需求，在两个不同模型（或两个 harness）上各跑一次，比对阶段结论与最终验收。

**Acceptance Scenarios**:

1. **Given** 同一需求与同一版本包，**When** 换模型执行，**Then** 两个执行者都通过验收，差异仅在耗时/措辞。
2. **Given** 某个执行者卡住，**When** 查阅文档，**Then** 文档能指出该情境该调用哪个工具、参数怎么给（不依赖提问者已有经验）。

---

### User Story 3 - 执行过程零一次性脚本 (Priority: P1)

整个画板过程，所有对工程的写入都来自**具名、可复用的命令或可回放 playbook**；不出现"这次特殊，先写个脚本"。

**Why this priority**: 一次性脚本正是过去 49 轮能力归零的根因；这条不成立，产品就退化成"又一个碰巧成功的过程"。

**Independent Test**: 审计运行日志：所有写入型操作都能对应到一个具名命令/playbook 条目；出现临时脚本即判失败。

**Acceptance Scenarios**:

1. **Given** 一次完整执行，**When** 审计日志，**Then** 一次性脚本数量为 **0**。
2. **Given** 需要一段多步链路，**When** 固化为 playbook，**Then** 该 playbook 可被下一次直接复用（有名字、有文档、被索引）。

---

### User Story 4 - 产出可打样的交付物 (Priority: P2)

用户拿到的是能直接下单的东西：Gerber、钻孔、坐标、BOM。

**Why this priority**: "画出板子"的字面含义包含可制造；画得再好看打不了样等于没画。

**Independent Test**: 在完成的板上导出制造文件，核对每类文件真的生成且非空，输出路径/大小/校验和；缺项如实标注。

**Acceptance Scenarios**:

1. **Given** 已完成布线的板，**When** 请求交付导出，**Then** Gerber、钻孔、坐标、BOM 均生成且非空。
2. **Given** 某类导出在本机不可用，**When** 请求它，**Then** 明确报"能力缺失"并指出缺口，不得伪造成功。

---

### User Story 5 - 能力边界诚实可查 (Priority: P2)

产品明确列出"做不到什么、为什么、替代路径是什么"，而不是让执行者在失败里反复试。

**Why this priority**: 过去大量时间浪费在"以为能做到"的尝试上（例如反复调参试图让单层求解器解出需要换层的跳线）。

**Independent Test**: 随机抽 5 条边界条目，逐条验证描述与实测一致（做不到的确实做不到，替代路径确实可用）。

**Acceptance Scenarios**:

1. **Given** 一条边界条目，**When** 按其替代路径执行，**Then** 得到条目描述的次优结果。
2. **Given** 一个需求触及边界，**When** 执行流程，**Then** 在早期阶段就报出边界与替代方案，而不是在最后失败。

---

### Edge Cases

- **需求超出工艺能力**（线宽/间距/层数不可实现）：应在早期阶段拒绝并给出可实现的最小改动建议。
- **扩展中心某个必需扩展未安装**：应报告"缺哪个、怎么装"，不静默降级。
- **EDA 窗口中途掉线/连接器版本不匹配**：应可恢复，且恢复动作本身是具名命令。
- **同一需求两次运行结果不一致**：视为缺陷（除时间戳类差异）。
- **板上已有用户手工改动**：不得覆盖，需先确认或只做增量。
- **需求涉及的器件在库里查不到**：应停下来要信息，不猜封装。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 产品 MUST 提供一份**情境→工具决策表**，覆盖扩展中心已装扩展、命令层与类型化动作，使执行者不需要凭经验猜测该调什么。
- **FR-002**: 产品 MUST 提供**分阶段流程文档**（原理图 S0–S6、PCB P0–P10），每阶段有进入条件、动作、退出判据与失败处理。
- **FR-003**: 产品 MUST 提供**一条命令可跑的验收**，对给定需求自动判定通过/失败，并指出失败发生在哪个阶段。
- **FR-004**: 产品 MUST 把所有多步链路固化为**可回放 playbook**（具名、带文档、被索引），不得依赖临时脚本。
- **FR-005**: 产品 MUST 提供**能力边界清单**，逐条写明：做不到什么、证据、替代路径。
- **FR-006**: 产品 MUST 可安装到至少两类环境：任意 harness 的 skill 目录；EasyEDA 扩展中心的分发形态。
- **FR-007**: 产品 MUST 在**不同模型**下产生一致结果（同一需求两次执行，阶段结论一致）。
- **FR-008**: 产品 MUST 在写入前做**可写性/几何前置校验**，避免"落了但没连上"被当成成功。
- **FR-009**: 产品 MUST 对**无法完成**的情况给出明确状态（缺能力/缺数据/需用户决策），与"失败"和"通过"三态分明。
- **FR-010**: 产品 MUST 优先复用扩展中心既有能力；新增自有工具时，MUST 在边界清单中记录缺口证据与复用不回退的理由。

### Key Entities

- **需求（Requirement）**: 客户对板子的自然语言描述 + 硬约束（层数、尺寸、接口、工艺）。
- **阶段（Phase）**: 流程中一个有进入/退出判据的步骤；可独立验收。
- **工具条目（Tool Entry）**: 一个可被调用的能力单元（扩展 / 命令 / 类型化动作 / playbook），含适用情境、参数、已知坑。
- **验收用例（Acceptance Case）**: 一份需求 + 期望结果 + 判定脚本。
- **边界条目（Boundary Entry）**: 做不到的能力 + 证据 + 替代路径。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在**两块此前未画过的板**上，全新会话零上下文，端到端通过验收；通过率 **2/2**。
- **SC-002**: 验收通过的含义是可核对的四项同时成立：原理图门禁通过、DRC 错误 **0**、DFM ERROR **0**、交付文件齐备。
- **SC-003**: 单次执行的**一次性脚本数量 = 0**（审计日志判定）。
- **SC-004**: 至少**一个不同模型**（或不同 harness）复跑其中一块板并通过，证明结果不依赖特定执行者。
- **SC-005**: 执行者遇到未覆盖情境时，决策表能给出可执行答案的比例 **≥ 90%**（抽查 20 个情境）。
- **SC-006**: 同一需求连续两次执行，阶段结论一致（允许耗时差异）。

## Assumptions

- 使用者已具备 EasyEDA Pro 环境，并允许安装扩展；扩展中心可访问。
- 产品依赖既有 CLI 与连接器扩展作为基础设施；它们可被独立安装与升级。
- 一次验收只覆盖**单块板**；拼板/多板不在首选版范围内。
- 网络可用的前提下，扩展可在运行前一次性装好；安装步骤属于文档而非每次执行。
- 器件选型允许在库里查不到时中断并向用户索取信息，不做猜测。
- 交付文件的格式以目标工厂（嘉立创）接受的格式为准。
