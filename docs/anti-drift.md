# 反目标偷换（anti-drift）

> 本文件定义本产品最重要的一条纪律，以及它的**机械判据**。
> 判据在 `acceptance/run.ps1` 的 `drift-guard` 阶段执行：**它失败，这一轮就不算数**。

---

## 1. 要防的那个错误，长什么样

**症状**：把「造出可复用的能力」偷换成「用一堆一次性工具把眼前这块板画出来」。

它不会自我暴露。它的表现是**看起来一直在推进**：

| 表面现象 | 实际发生了什么 |
|---|---|
| 每轮都有新进展、数字在变好 | 进展是一次性的，换块板/换个模型就归零 |
| 写了"工具" | 写的是只服务这一次的脚本，没有名字、没被索引、没有验收 |
| 文档越来越长 | 长的是过程记录，不是别人能照着做的流程 |

**实测代价（前 49 轮）**：一次性脚本 26 个、一次性 playbook 28 个；同一句纪律
写过 2 次、违反 2 次；板子最好状态靠手搓达成，两次操作后退回原点。

---

## 2. 为什么"提醒自己"没用

同一句「不要对着旧快照求解多对」我写进台账两次，又违反了两次。
**能被遵守的约束，是能失败的检查；不是写得好的原则。**

所以本产品不靠自觉，靠下面三条机械判据。

---

## 3. 三条判据（`drift-guard` 阶段）

### a) 仓库里不许存在一次性产物

判据：仓库内出现下列任一即 **FAIL**

- `.work/`、`scratch/`、`tmp/`、`oneoff/`、`_scratch/` 目录
- 匹配 `*gen*.py`、`*apply*.json` 的文件（`playbooks/` 内除外）
- **`acceptance/` 之外**、内容里调用 `easyeda` 的 `*.py` / `*.ps1` 脚本

理由：这些文件的共同点是**只服务一次**。它们一出现，就说明这一轮在工作区画板，
而不是在让产品变强。

### b) 最近一次提交必须动到规范产物

判据：`git show --name-only HEAD` 里必须至少有 1 个路径落在
`docs/`、`playbooks/`、`acceptance/`、`specs/` 之下，否则 **FAIL**。

理由：只改板子、只加临时文件的提交，不产生可复用能力。

### c) 规范产物数量只能增，不能减（棘轮）

判据：与 `acceptance/baseline.json` 比对，`docs/`、`playbooks/`、`acceptance/`、`specs/`
四类文件数**任一减少即 FAIL**。

理由：删文档换"清爽"、删 playbook 换"简化"，也是能力退化。基线只允许上调。

---

## 4. 每轮怎么用

每轮结束前必须做两件事，且都要留下**脚本输出**而不是叙述：

1. 跑 `acceptance/run.ps1`；
2. `drift-guard` 必须 **PASS**。

只要它是 FAIL，这一轮的产出就**不算**——无论板子看起来多好。

---

## 5. 允许的例外（写在这里，避免现场编例外）

| 情况 | 处置 |
|---|---|
| 需要验证某个一次性做法能否解决问题 | 在 `acceptance/tools/` 或 `playbooks/` 下写**具名**条目，而不是随手 `.work/` 脚本 |
| 板子必须当场修一下 | 用现有命令/playbook；若现有工具做不到，这本身就是 `docs/capability-boundary.md` 的一条缺口记录 |
| 探究性读取（只看不写） | 允许，因为它不修改工程、也不产生一次性产物 |

---

## 6. 与验收其余阶段的关系

`drift-guard` 是**独立的常驻门禁**：它不需要工程、不需要 EDA 窗口，任何时候都能跑。
其余阶段（连接、布局、DFM、交付）反映的是**产品当前能力**；`drift-guard`
反映的是**这一轮有没有在真正提升产品**。

两者必须同时成立：能力没提升 → drift-guard 会抓到；提升了但产品还做不到 → 其余阶段 FAIL，
那是正常的当前状态。

---

## 7. 门禁是双向的

只有"抓错"不够——一个只会抓错的门禁，在我不犯错时永远绿灯，等于没有正向要求。
所以 `acceptance/run.ps1` 里有两组常驻判据，**都必须 PASS**。

### 正向 `positive-goal`：这一轮是不是在长产品能力

| 编号 | 判据 | 抓的是什么 |
|---|---|---|
| P1 | `docs/` `playbooks/` `acceptance/` `specs/` 文件数只增不减（对照 `baseline.json`） | 用"整理/精简"掩盖能力退化 |
| P2 | `playbooks/` 里每个 `*.playbook.json` 必须含 `version`/`meta`/`steps` 且 steps 非空 | 把一段说明文字冒充成"可回放链路" |
| P3 | kit 仓库内不许出现 `*.go` / `*.ts` / `*.js` 实现类源文件 | 又开始手搓布线器/DFM，而不是复用扩展中心 |
| P4 | `spec.md` 里可测量判据（`SC-0xx`）≥ 3 条 | 验收标准退化成形容词 |
| P5 | 三态语义未被破坏（BLOCKED 不算 PASS，交付物查非空） | 用 BLOCKED 冒充通过 |

### 负面 `negative-drift`：有没有再犯以前跑偏的错

每条都对应一次**真实事故**：

| 编号 | 判据 | 对应事故 |
|---|---|---|
| N1 | 仓库内不得有 `.work/`、`*gen*.py`、`*apply*.json`、acceptance 外调用 easyeda 的脚本 | 26 个一次性生成器 + 28 个一次性 playbook，能力归零 |
| N2 | 最近一次提交必须动到规范产物 | 大量"只改板子"的轮次 |
| N3 | 仓库内不得出现自建检查器实现（`*.go`/`*.py` 含 clearance/drc/dfm） | 用自写 DFM 给自己开绿灯 |
| N4 | 运行日志里不得出现 `rip-up --net` | 第 46 轮整网被删，Connection 21→31 |
| N5 | 求解次数 ≤ 取快照次数 | 第 43/46 轮对着旧快照求解，Clearance 18→31 |
| N6 | `save` 之后、`drc` 之前必须有 `doc reload` | 第 20/36/46 轮读到中间态并据此下结论 |

N4–N6 需要 `-RunLog`；**没有日志时报 BLOCKED，不报 PASS**——无法审计就不算通过。

### 门禁自身的回归测试

`acceptance/fixtures/` 放了两份运行日志：

- `runlog-drifted.txt` —— 复刻三类事故，`negative-drift` 必须 **FAIL**
- `runlog-clean.txt` —— 正确做法，必须 **PASS**

改门禁后必须两种都跑一遍：**能失败的门禁才是门禁**。
